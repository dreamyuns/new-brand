픽콕 리워드 어드민 기능정책서 v0.2

문서 성격 — 리워드(포인트) 운영을 위한 어드민 기준 문서다. 기존 신규_mvp_어드민_v0.9.md는 메타서치 어드민(회원·예약내역·이메일 템플릿)을 다루며, 리워드 메뉴(출금·픽샵·혜택·광고주·퀴즈·알림)는 그 문서에 한 건도 없다. 이 문서가 리워드 어드민의 기준이다.

작성 근거 — 이 문서의 메뉴·열·상태값·설정값·제외 항목은 2026-10-12 시점 구현물에서 직접 뽑았다. 기억이나 추정으로 적은 값은 없다. 아직 정해지지 않은 것은 미결로 표시했고, 값을 적지 않았다.

제1조 (목적과 범위)

1-1. 목적

고객이 출석·퀴즈·혜택·친구 추천·숙소 예약으로 쌓은 포인트를 운영자가 확인·조정·지급하고, 적립 거리를 개발자 없이 넣고 뺄 수 있게 한다.

제2조 (로그인과 권한)

2-1. 로그인

  • 비밀번호 하나로 들어간다. 계정 구분이 없다.
  • 비밀번호는 설정(admin_pw)에서 바꾼다.

2-2. 권한 — 현재 없음

항목 현재 정해야 할 것
계정 구분 없음 (단일 비밀번호) 운영자별 계정 발급 여부
권한 등급 없음 (들어오면 전부 가능) 조회 전용 / 처리 가능 구분
처리자 기록 남지 않음 관리자 로그에 처리자를 남기는 방식

미결 — 포인트 수동 지급·회수와 출금 지급은 돈이 움직이는 행위인데 지금은 누가 했는지 알 수 없다. 권한 체계와 함께 정해야 한다.

2-3. 로그인 직후 안내

로그인하면 안내 팝업이 한 번 뜬다 (탭마다 1회). 이번 버전의 성격(시연용·가상 데이터)과 빠진 기능이 있다는 점을 먼저 알리고, 기능정책서로 가는 링크를 둔다.

왜 — 운영자가 완성된 어드민으로 알고 들어오면 빠진 기능마다 문의가 발생한다. 미리 알리는 편이 싸다.

  • 공지·참고 사항도 같은 모양으로 통일한다

  • 픽샵의 「총 구매」는 취소분을 뺀 값이다

왜 미사용을 따로 보나 — 픽샵의 미사용 금액은 앞으로 쿠폰 업체에 정산해야 할 채무다. 쓴 것과 섞으면 남은 채무를 알 수 없다.

3-4. 불러오는 중

  • 자료를 가져오는 데 0.22초를 넘길 때만 자리를 잡는 회색 틀이 나온다
  • 그보다 빠르면 아무것도 보이지 않는다
  • 못 가져온 경우에는 사유와 [다시 시도] 버튼이 나온다

왜 지연 방식인가 — 실측 결과 화면 전환이 29~101ms였다. 무조건 띄우면 번쩍거려 오히려 지저분하다.

제5조 (회원 관리)

5-1. 목록

열: 선택 · 회원ID(이메일) · 이름 · 본인인증 · 추천코드 · 추천한 친구 · 보유 포인트 · 가입일 · 관리

  • 찾기: 가입일(달력) · 본인인증(전체/완료/미완료) · 검색어(이메일·이름·추천코드)
  • 회원 ID는 이메일 주소다. 별도 아이디를 두지 않는다
  • 보유 포인트 — 적립대기 표시 (v0.2): 미인증 회원인데 (원장 잔액 + 적립대기)가 1 이상이면 그 합계를 보여주고 오른쪽에 작은 「적립대기」 를 붙인다 (예: 「500P 적립대기」). 인증 회원·0P 는 원장 잔액 그대로

적립대기 — 로그인했지만 본인인증 전인 회원에게 생긴 적립(예약 적립 · 친구 추천 · 관리자 지급). 원장에 넣지 않고 기다렸다가 본인인증하는 순간 한꺼번에 지급한다(기한 없음 · 적립일 = 지급일). 상세는 참여형적립 기능정책서 1-6절

5-2. 상세

좌우 두 단으로 기본 정보와 포인트 내역을 함께 본다.

  • 미인증 회원 (v0.2) — 포인트 요약의 「사용 가능」 대신 「보유 NP 적립대기」 를 보여주고, 그 아래 안내 「본인인증 전이에요. 아래 포인트는 고객 화면에 보이지 않고, 본인인증을 하면 그때 지급돼요.」 와 내역 칩(예약 · 친구 추천 · 관리자 지급·회수 · 이전에 쌓인 포인트 — 각 금액·건수)을 둔다

5-3. 포인트 수동 지급·회수

  • 목록에서 회원을 골라 한 번에 처리할 수 있다
  • 금액과 사유를 적어야 한다. 사유는 원장에 그대로 남는다
  • 처리하면 원장에 한 줄로 쌓이고, 관리자 로그에도 남는다(point_grant)
  • 미인증 회원 (v0.2 · PO 확정 2026-10-27) — 지급·회수할 수 있다. 다만 적립대기로 들어가고, 본인인증을 해야 고객 화면에 보이고 실제로 적립된다
    • 미인증 회원에게는 지급·회수 알림을 보내지 않는다 (금액이 드러나므로). 인증으로 지급될 때 「적립대기 포인트 +NP」 1건
    • 회수는 (원장 잔액 + 적립대기) 안에서만 — 넘으면 「회수할 포인트가 모자라요 (적립대기 포함)」
    • 결과 안내: 단건 「본인인증 전 회원이라 적립대기로 넣었어요 · 인증하면 지급돼요」 / 일괄 「N명 처리 완료 · 그중 N명은 본인인증 전이라 적립대기」

미결 — 권한·한도·처리자 기록이 정해지지 않았다. 지금은 누구나 금액 제한 없이 지급·회수할 수 있다. (2-2 참조)

5-4. 본인인증 처리 (v0.2 신설)

  • 회원 상세에서 관리자가 본인인증 상태를 완료로 바꿀 수 있다 (시연용)
  • 완료로 바꾸면 고객이 직접 인증한 것과 같이 적립대기를 지급한다 · 관리자 로그에 「본인인증 완료 · 적립대기 NP 지급」

5-5. 계정 통합 (v0.3 신설)

왜 어드민에 남기나 — 통합은 되돌릴 수 없고 포인트가 합쳐진다. 고객 화면에는 간단한 이력만 보이므로, 분쟁·문의 때 답할 수 있는 근거는 어드민 기록뿐이다. (앱 정책 01-3 1-6-8 안전장치 3 · 회원 정책 v0.2 3-2)

자리 보여주는 것 근거
목록 — 이메일 칸 통합한 회원은 이메일 옆에 「통합 N」 배지, 그 아래 합쳐져 사라진 이메일(↳ 표시) [PO 확정 2026-10-27]
목록 — 찾기 사라진 이메일로도 찾아진다. CS 문의는 대개 예전 이메일로 들어오는데, 그 주소는 고객 화면에서 사라져 그냥 두면 「그런 회원 없음」이 된다 [PO 확정 2026-10-27]
상세 — 「계정 통합 N건」 통합 일시 · 통합에 쓴 수단 · 합쳐진 계정(이메일·회원번호·가입일) · 이관 포인트(적립완료 / 적립예정) · 여러 번이면 전부(최신순) 01-3 1-6-8
상세 — 안내 「되돌릴 수 없어요. 합쳐진 이메일로도 계속 로그인할 수 있고, 이관된 포인트는 아래 원장에 「계정 통합 이관」으로 남아 있어요.」 [구현]

제6조 (전체 포인트 내역 — 원장)

6-1. 원칙 — 잔액을 저장하지 않는다

  • 잔액은 그 줄들을 더한 결과다
  • 이 화면은 보기만 하고 고치지 않는다

왜 — 기록을 고칠 수 있으면 기록이 아니다. 포인트를 바꿔야 하면 회원 상세에서 사유를 적어 처리하고, 그 행위 자체가 또 한 줄로 쌓인다. 지우는 길을 만들지 않는 것이 핵심이다.

제7조 (출금 신청)

7-1. 흐름

  1. 고객이 신청하면 포인트가 즉시 차감된다 (withdraw)
  2. 운영자가 회원·금액·계좌를 확인한다
  3. 실제로 송금한 뒤 [지급하기] 를 누른다
  4. 문제가 있으면 [반려] 를 누른다 → 차감한 포인트가 바로 환불된다 (cancel_refund)
  • 사전 승인 단계는 없다. 처리대기 건을 [지급하기] 또는 [반려] 둘 중 하나로 끝낸다
  • 지급·반려 모두 고객에게 알림이 간다

7-2. 반려 사유 (필수)

사유 성격

제8조 (픽샵 구매내역)

8-1. 원칙 — 자금 이동이 없다

포인트로 쿠폰을 바꾸는 것이라 승인 절차를 두지 않는다. 구매 즉시 쿠폰이 자동 발행된다.

8-2. 운영자가 하는 일

  • 쿠폰번호 재발행 — 고객의 쿠폰번호 분실이 실제로 잦다
  • 취소 건 확인 — 취소하면 포인트 환불 + 재고 복구
  • 고객이 쿠폰을 쓰고 [사용 처리]를 누르면 사용완료로 바뀐다

8-3. 상태

구매완료 · 사용완료 · 구매취소 · 발행실패

8-4. 열

미결 — 쿠폰 발행 업체가 정해지지 않았다. 현재 쿠폰번호는 자사에서 만들어 보여주는 것이다.

제9조 (예약 적립)

9-1. 구조

숙소 예약으로 예약처가 지급하는 재원을 기본 적립과 뽑기 둘로 나눈다.

몫 현재 값 지급 시점
기본 적립 예약금액의 1% (draw_base_rate) 예약 즉시
뽑기 몫 나머지 고객이 뽑기를 해야 지급

왜 나누나 — 예약 적립은 자사 비용이 아니라 예약처가 주는 재원이다. 뽑지 않은 금액은 비용 절감인 동시에 고객이 받지 못한 금액이다. 이 수치가 계속 늘면 뽑기 안내가 부족하다는 뜻이다.

9-2. 열

9-3. 숙박일을 함께 보는 이유

적립이 확정되는 시점은 예약한 날이 아니라 숙박을 마친 뒤다. 예약처가 보내 주는 자료에도 체크인·체크아웃 날짜가 담겨 있어 대조 기준이 된다.

9-4. 찾기

  • 날짜 기준: 숙박일 / 적립일 → 기간(달력)
  • 뽑기: 전체 / 미수령 · 검색어

9-5. 상태

적립완료 / 취소 둘로만 구분한다. 「적립예정」 단계를 두지 않는다.

  • 예외 — 적립대기 (v0.2): 본인인증 전 회원의 예약. 예약은 기록하되 포인트는 지급 전이다. 「총 적립」 칸에 「적립대기」 배지 + 「본인인증 전 · NP」, 위쪽 합계에서는 빠진다. 인증하면 적립완료 로 바뀌고 뽑기가 열린다

미결 해소 2026-10-27 — 뽑기 가능 기간 적립완료일 + 30일(draw_expire_days=30) · 포인트 정책서 v0.2 4절. 정책상 30일 예정이나 확정되지 않았다.

실제 운영에서는 호텔스컴바인이 예약 결과를 알려준다. 시연에서는 고객이 아웃링크 화면에서 [예약 완료 처리]를 눌러 만든다. 실연동 시에는 확정까지 수개월이 걸리고 누락되는 건도 있다.

  • 이미 푼 문항은 기간 없이 제외된다. 설정 「푼 문제 다시 출제 허용」 을 켜면 제외를 풀고 모든 회원에게 다시 출제한다 (2026-10-26 PO 확정 · v0.2 구현 완료 — quiz_allow_repeat)

  • 광고를 「사용」으로 두면 링크가 있어야 저장된다 — 없으면 「광고를 사용하려면 광고 링크를 입력해 주세요」 (v0.2)
  • 같은 문장의 문항은 등록·수정할 수 없다 — 「이미 등록된 문항이에요」 (v0.2 · 엑셀 등록은 이미 건너뛰고 있었음)
  • 문항 창의 해설 칸 이름 = 「해설 (정답 공개 후 항상 보여줍니다)」 — 고객 화면은 정답·오답 모두 해설을 보여준다 (v0.2)

미결 — 출제 근거를 무엇으로 담보할지. 근거 URL 입력란은 v0.6에서 없앴다. 문항별 광고 표기 의무도 확인이 필요하다.

12-1. 출석 보너스 하한 7%

최고 구간(71~100P)의 비중을 7% 미만으로 내리지 못하게 막아 두었다.

⚠️ 이 7%는 법으로 정해진 수치가 아니다. 표시광고법은 구체적인 비율을 규정하지 않는다. 「최대 100P」라고 알리면서 그 확률이 지나치게 낮으면 문제가 될 수 있다는 판단에서 자사 기준으로 정한 값이다. 미결 — 법무 검토 필요.

12-2. 데이터 초기화 (시연 전용)

  • 포인트·기록만 초기화 / 전부 초기화(회원까지)
  • 시연 반복을 위한 기능이다. 상용에서는 제거한다.
